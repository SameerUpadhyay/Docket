# AWS pilot deployment

Selected by the project owner on 25 October 2026. Default region: **Mumbai `ap-south-1`**. This folder prepares AWS deployment; **no account has been connected and no resources have been created**. There are no configured AWS profiles in the current workspace. Domain, Route53 zone, operator support address and AWS SSO/profile access remain necessary.

## Reviewable infrastructure

`cloudformation.json` is generated by `scripts/aws_template.py` and statically validated with `cfn-lint` for Mumbai. It declares:

- Private application/database subnets across two availability zones; an HTTPS Application Load Balancer, ACM DNS certificate and Route53 app record. Only the load balancer accepts public requests. One NAT gateway supports outbound image pulls/signature updates/provider access. The single NAT is a pilot availability tradeoff; use one per AZ for stronger resilience.
- Encrypted, private RDS PostgreSQL, 14-day automated backups, deletion protection and snapshots on replacement/deletion. Choose Multi-AZ for production availability. The initial application count is zero. RDS selects its supported default PostgreSQL version; confirm and pin an accepted minor version in infrastructure review before operating a long-lived production service.
- Restricted application database credentials generated in Secrets Manager. A separate one-off bootstrap task may read the RDS master secret to create the application role; the normal API/worker cannot read that master secret. Application encryption material is a persistent random Secrets Manager value, derived into the Fernet data key. Keep it and the KMS key with restore procedures.
- Private KMS-encrypted S3 storage, Block Public Access, HTTPS-only bucket policy, versioning, 30-day expiration of noncurrent versions and private object IAM. Deleted objects leave retained historical versions until this period expires. Database, bucket and keys are intentionally retained/protected rather than silently destroyed on stack removal.
- ECS Fargate application task with native API, local ClamAV, browser companion and reminder worker; ECR repositories, immutable image tags and image scanning. API/worker use workload IAM for **SES API delivery** and private S3; SMTP access keys are unnecessary. API temporary storage is initialized with safe writable permissions before its read-only container starts.
- SES domain identity, DKIM records, a configuration set with bounce/complaint suppression and reputation metrics. SES sandbox removal and verified production sending remain account-level acceptance gates. Publish your reviewed SPF/custom MAIL FROM/DMARC policy before release; the template does not overwrite an existing domain mail policy.
- CloudWatch logs, ALB 5xx/worker heartbeat/delivery-failure/database-space alarms, optional SNS operator subscription, and a WAF request rate rule. Configure the alert subscriber and confirm its subscription. Worker metrics contain counts only. WAF sampling is disabled to avoid retaining uploaded case content.

The application task shares a task role and network with its sidecars. For a larger public deployment, split web/API/worker into separately permissioned services, add autoscaling and stronger egress controls, perform threat modeling and independently test the result.

## Staged operator workflow

1. Sign in through an AWS SSO/profile with appropriate deployment permissions. Create/identify the owned Route53 zone. Do not put access keys or database passwords in source, shell arguments or chat.
2. Copy `parameters.example.json` to an operator-local file and replace domain, zone and email placeholders. These parameters contain no secrets. Keep `DesiredCount=0`; initial placeholder images are **never run**. Review every resource and obtain a current estimate for RDS, NAT, ALB, ECS, WAF, logs, secrets, storage, DNS and email with the AWS Pricing Calculator. Set an AWS Budget and named operator before execution. No price/budget has been assumed by this implementation.
3. Create a change set, without executing it:

   ```sh
   backend/.venv/bin/python scripts/aws_pilot.py --profile YOUR_SSO_PROFILE plan --parameters /path/to/parameters.json
   ```

   Review the change set in CloudFormation. Executing it creates paid infrastructure, DNS records and IAM roles. Only after owner approval:

   ```sh
   backend/.venv/bin/python scripts/aws_pilot.py --profile YOUR_SSO_PROFILE execute --change-set REVIEWED_CHANGE_SET_ARN --approve-paid-resources
   ```

4. After infrastructure creation, publish immutable amd64 images to the returned ECR repositories with Docker/buildx:

   ```sh
   backend/.venv/bin/python scripts/aws_pilot.py --profile YOUR_SSO_PROFILE images --tag pilot-001
   ```

   Update the parameter file to the printed image URIs, keep `DesiredCount=0`, create/review/execute another change set. Verify image scan results and pin the ClamAV image digest as well. The helper logs out of ECR when finished and never prints registry credentials.
5. Initialize the restricted database user:

   ```sh
   backend/.venv/bin/python scripts/aws_pilot.py --profile YOUR_SSO_PROFILE bootstrap-database
   ```

   Wait for ECS exit code 0. Re-running does not rotate credentials; credential rotation needs an explicit coordinated database/secret update. Then set `DesiredCount=1` in a newly reviewed change set. Confirm migrations, uploads, worker heartbeat and all alarms. Signature downloads may initially delay ClamAV readiness; uploads fail closed until scanning works.
6. Verify SES DKIM status, send to real owned test recipients, complete sandbox removal, bounce/complaint suppression and unsubscribe/consent procedures. Verify no notice content is included in reminders. Alarm/email production access is not established merely by deploying the template.
7. Complete legal policies/playbook approval, independent security review, encrypted backup restore/deletion replay and physical-device acceptance. Connect the Android app to the final HTTPS URL; produce a privately signed app bundle for Play.

`status` prints infrastructure status and nonsecret outputs. The helper uses boto3 and normal AWS profile/SSO credentials. Neither AWS CLI nor Docker was installed in the current workspace, so image publishing, change-set creation and live provisioning were not exercised.

## Bilingual OCR configuration

Application images contain local English/Hindi Tesseract models verified against committed SHA-256 hashes. The template selects `OCR_PROVIDER=gemini`, but original images are not sent externally until a workspace owner opts into Cloud OCR. An optional `GeminiSecretArn` parameter injects a Gemini API key from Secrets Manager. Without a usable key/model the local fallback is used and flagged. Confirm access to the configured model: Google currently limits Gemini 2.5 access for new projects; `GEMINI_OCR_MODEL` can be changed in the task environment after evaluation. This is an additional Google processor alongside AWS RDS/S3/SES. Summary consent and original-retention consent remain separate. The optional Textract adapter supports English only; Hindi uses the bilingual path. No live cloud OCR call was exercised. See [OCR setup, benchmark failures and acceptance gates](../../docs/bilingual-ocr.md).
